# FITX REST API

This guide defines the public contract between the Next.js client and `FITX.API`. OpenAPI/Swagger generated by the running Development API is the field-level source of truth; this document captures conventions, authorization, semantics, and the intended endpoint catalogue.

## Base addresses

- Local browser URL: `http://localhost:8080/api`
- Compose-internal URL: `http://api:8080/api`
- Development Swagger: `http://localhost:8080/swagger`

All business endpoints are under `/api`. HTTPS is mandatory outside local development.

## JSON and data conventions

- Request and response property names use `camelCase`.
- Entity identifiers are GUID strings. Human-facing identifiers such as `memberCode` and `paymentNumber` are separate.
- Instants use ISO 8601 UTC offsets, for example `2026-09-11T08:30:00Z`.
- Membership start/expiry and report date filters use ISO dates, for example `2026-09-11`.
- Money is a JSON number backed by server-side `decimal(18,2)`; callers must not send formatted strings such as `Rs. 2,000`.
- Enum values use stable English names such as `Active`, `ExpiringSoon`, `Paid`, and `WhatsApp`. The client localizes display labels.
- Unknown JSON fields must not be used to bypass validation. Server calculations override client previews.

## Response envelope

Successful single-resource response:

~~~json
{
  "success": true,
  "data": {
    "id": "2c8646a0-c7aa-45bb-a9ca-ea4c390a95fd"
  },
  "message": "Member created.",
  "errors": null
}
~~~

Failed validation response:

~~~json
{
  "success": false,
  "data": null,
  "message": "The request is invalid.",
  "errors": {
    "amountPaid": ["Payment amount cannot exceed the remaining balance."]
  }
}
~~~

Paged `data` uses:

~~~json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "totalCount": 0,
  "totalPages": 0
}
~~~

Every response should include or expose an `X-Correlation-ID`. Include that ID when reporting a server error.

## Authentication

Send the access token on protected requests:

~~~http
Authorization: Bearer <access-token>
~~~

Access tokens are short-lived. Refresh tokens are opaque rotating credentials; clients must not decode or log them. The preferred browser transport is a Secure, HttpOnly, SameSite cookie. If the implementation returns a refresh value in JSON for non-browser clients, it must be stored in platform-secure storage, never local storage.

| Method | Route | Access | Purpose |
| --- | --- | --- | --- |
| POST | `/api/auth/login` | Anonymous, rate-limited | Authenticate email/password and issue a session |
| POST | `/api/auth/refresh` | Refresh credential | Rotate refresh token and issue access token |
| POST | `/api/auth/logout` | Authenticated/session | Revoke current refresh token |
| POST | `/api/auth/forgot-password` | Anonymous, rate-limited | Begin recovery; always return a generic result |
| POST | `/api/auth/reset-password` | Valid reset token | Set password and revoke existing sessions |
| GET | `/api/auth/me` | Any authenticated role | Current user, role, permissions, and locale |
| PATCH | `/api/auth/me` | Any authenticated role | Update own profile/locale |
| POST | `/api/auth/change-password` | Any authenticated role | Change own password and revoke other sessions |

Example login:

~~~json
{
  "email": "admin@fitx.local",
  "password": "Fitx@123",
  "rememberMe": false
}
~~~

Production must never expose or seed this development credential.

## Authorization shorthand

- **O**: Owner
- **A**: Admin
- **S**: Staff
- **Public**: no authenticated identity

An endpoint marked O/A/S may still apply record-level and state validation. UI hiding never replaces API authorization.

## Query conventions

List endpoints use these common parameters when applicable:

| Parameter | Meaning |
| --- | --- |
| `page` | One-based page; default 1 |
| `pageSize` | Default 20, maximum 100 |
| `search` | Trimmed free-text search |
| `sortBy` | Endpoint-specific allowlisted field |
| `descending` | Boolean sort direction |
| `from`, `to` | Inclusive local calendar dates |

Invalid sort fields return 400 rather than becoming dynamic SQL. Report queries interpret `to` as the final included local day and convert it to a half-open UTC range internally.

Common optional filters:

- Members: `membershipStatus`, `paymentStatus`, `planId`.
- Payments: `memberId`, `planId`, `status`, `paymentMethodId`, `from`, `to`.
- Expenses: `categoryId`, `paymentMethodId`, `from`, `to`.
- Reminders: `type`, `channel`, `status`, `from`, `to`.

## Localization

Send `Accept-Language: ur` or `Accept-Language: en` for server-authored messages, receipts, reports, and reminder previews. Business data such as names, IDs, phone numbers, email, and amounts is unchanged. Error codes/field keys remain stable across languages.

## Duplicate-submission protection

`POST /api/payments`, `POST /api/renewals`, and other sensitive create operations accept:

~~~http
Idempotency-Key: <client-generated-uuid>
~~~

The same authenticated user, route, and key with the same body returns the original successful result. Reusing the key with a different body returns 409 Conflict. The web client disables a submitting control as immediate feedback, but API idempotency is the authoritative protection.

## HTTP status codes

| Code | Meaning |
| --- | --- |
| 200 | Successful read/update/action |
| 201 | Resource created; include `Location` where practical |
| 204 | Successful action with no body |
| 400 | Malformed input or validation failure |
| 401 | Missing, invalid, or expired authentication |
| 403 | Authenticated but not permitted |
| 404 | Resource absent or intentionally hidden |
| 409 | State conflict, duplicate key, stale balance, or idempotency mismatch |
| 422 | Well-formed request violates a domain rule, when distinguished from 400 |
| 429 | Rate limit exceeded; include `Retry-After` |
| 500 | Unexpected failure with generic text and correlation ID |

Never return exception stack traces, SQL details, token values, password hashes, or provider secrets to clients.

## Concurrency and financial writes

Payment and renewal services re-read the current membership/balance inside their transaction. A stale client calculation produces 409 with the current safe summary so the form can refresh. Two simultaneous payments cannot both spend the same outstanding balance.

Edits/deletions to financial records are audited. Payment correction is a void operation followed by a new payment when appropriate, preserving receipt history. Expense deletion is soft. Audit snapshots redact credentials, tokens, password hashes, and sensitive national ID data.

## Caching

Authenticated financial responses default to `Cache-Control: no-store`. Immutable generated exports may use short-lived signed storage URLs, but must remain authorization-scoped. Lookup lists may use ETags. A write invalidates affected dashboard/report caches.

## OpenAPI maintenance

All public controllers should provide enough metadata for Swagger to show:

- summary and authorization;
- request/response DTOs;
- validation constraints and enum values;
- success/error status codes;
- pagination/filter parameters;
- download content types.

The frontend should consume typed DTOs generated from or checked against OpenAPI where practical. Contract changes should remain backward compatible within the current API version or introduce an explicit new version.
